# AI Doubt Solver, Limits and Safeguarding Implementation Plan (Plan 5a)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Also follow `AGENTS.md`. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A student taps "मुझे समझ नहीं आया" on any lesson or practice screen, types a doubt (online or offline), and gets a short answer from `claude-haiku-5-5` on the same screen; limits, safeguarding alerts, mentor visibility and cost reports come with it. This plan also builds the shared pieces Plans 5b and 6a use: `server_jobs` and its runner, `org_settings`, `requireFeature`, and the `AIProvider` and `Email` ports.

**Architecture:**

- **The doubt is an outbox event.** The phone appends `doubt_asked` (the text is in the event) and pushes it with the normal sync. `pushEvents` hands each new `doubt_asked` to `ingestDoubts`, which writes a `doubts` row and decides: safeguarding (keyword list), off (switch or a limit of 0), over the limit, or queue a `doubt_answer` job. The push never calls the AI.
- **Answers come back as a server-written `doubt_answered` event**, pulled like `level_set`. Its event id is fixed when the doubt row is made, so a job that runs twice writes one answer.
- **Jobs** are rows in `server_jobs`, run by `runDueJobs`: right after a push in the Edge Function's background (`EdgeRuntime.waitUntil`), and as a safety net by a scheduled GitHub Actions workflow (`npm run admin -- run-jobs`). At-least-once; every handler is idempotent.
- **Lesson text** for the prompt comes from the published content (the same `manifest.json` and module bundles the phones download from `CONTENT_BASE_URL`), checked by SHA-256, through a `LessonSource` port.

**Tech Stack:** Unchanged (Svelte 5, Vite PWA, Dexie, Supabase Postgres/Auth/Edge Functions, `postgres`, Zod 4, Vitest, Playwright). No new npm dependency: the Anthropic and Gmail adapters use `fetch` and WebCrypto, which run in both Deno and Node.

## Global Constraints

Everything marked _(builder's call)_ is open in the spec; ⚑ marks a value the owner confirms (listed at the end).

- All Plan 3a–4b constraints still apply (layers, ports and adapters, identity from the token, Zod at every boundary, parameterised SQL, RLS per role, error codes, ids-only logs, size limits).
- **From the series map (Global Constraints 1–11), each applied here:** contract tests on memory and Postgres with more rows than one page (1); an old phone never loses new server data (2); derived data recomputed or corrected on read (3); revocation tested (4); signed-in staff surfaces keep `idleGuard` and no secret in `localStorage` (5); six steps for every personal-data table (6); one audit entry per write route, ids and keys only (7); both ends traced (8); first-load JS budget 120 KB and a lazy chunk per new student screen (9); no names in URLs, id cursors (10); server-side `FEATURE_OFF` via `requireFeature`, tested with an un-synced phone (11).
- **AI model:** `claude-haiku-5-5` for doubts (rule). The key `ANTHROPIC_API_KEY` is env only (function secret and Actions secret). CI never makes a live call.
- **Before sending:** server checks the `ai_doubts` switch and the effective limit; masks phone numbers, emails and the learner's own name (each name word, loaded at send time; students type "My name is …" in English lessons); sends no name, email or id. The phone sends no lesson text.
- **Prompt:** student text inside `<doubt>…</doubt>`, with `<` and `>` in the student's text replaced by `‹` and `›` so it cannot close the tag; told to treat it as a question, never as instructions; keep to English, aptitude, the current lesson and job-related study; off-topic → a polite Hindi redirect; at most 4 short sentences at the student's `hiRatio`, English terms with Devanagari pronunciation (§6.2).
- **Output:** the model replies with one JSON object `{"kind":"answer"|"off_topic"|"distress","answer":string}`; parsed with Zod; `answer` 1–700 characters after trimming, control characters removed. Anything else is invalid output (retried). Never rendered as HTML anywhere (Svelte text only).
- **Effective limit** = `min(override ?? cohortDefault, orgMax)`; `cohortDefault` starts at **10** ⚑, `orgMax` default **30** ⚑, override `0` = off for that student. Counted per student per **IST day of server receipt** _(builder's call: the phone's clock is the student's to change)_, counting doubts sent to the AI (`queued`, `answered`, `failed`).
- **Burst limit** _(builder's call)_: `LIMITS.doubt = { limit: 20, windowSeconds: 600 }`, bucket `doubt:<learnerId>`; past it the doubt is stored as `over_limit` and not sent.
- **Doubt text:** 1–500 characters (`MAX_DOUBT_CHARS`, builder's call). **Kept 13 months** ⚑ after receipt, then the `doubts` row is deleted and the text in the event log is blanked (see "Where the text lives").
- **Safeguarding:** never counselling. Fixed caring reply with **Tele-MANAS 14416** and **Childline 1098** (wording ⚑, owner and a mentor), doubt flagged, needs-attention reason `'safeguarding'`, and a `safeguarding_email` job to `org_settings.safeguarding_email`. Checked first, before the switch and the limit: a distress doubt is never dropped for being over the limit or switched off. The keyword list and reply ship as a **PLACEHOLDER** structure (Task 2); the owner and a mentor write the real ones.
- **Jobs:** payloads hold ids only (refused otherwise); backoff `min(2^attempts, 360)` minutes; **max 8 attempts** ⚑ then dead (kept, counted on the settings screen); lease 5 minutes; done and dead rows pruned after 30 days. Schedule ⚑ (recommended every 30 minutes; see Notes).
- **Audit actions added:** `org_setting_changed` `{ key }`, `doubt_limit_changed` `{ cohortId, limit }` or `{ limit }`, `doubt_flagged` `{ doubtId, wrong }`, `doubt_acknowledged` `{ doubtId }`. Never a value of the safeguarding email, never doubt text.
- **No new `ApiError` codes:** a refused doubt is an outcome in its answer event, shown in plain Hindi.

### Where the text lives (append-only log, export, delete, retention)

- `learner_events` holds `doubt_asked.data.text` and `doubt_answered.data.answer`: the phone's history, pulled to a second phone like every event.
- `doubts` holds the server's working copy (status, the same text, the answer, marks) for jobs and mentors.
- **Retention** deletes `doubts` rows received more than 13 months ago and calls `EventRepo.redactDoubtText(cutoff)`, which sets `text`/`answer` to `''` in `doubt_asked`/`doubt_answered` events received before the cutoff. This is the **one permitted edit** of the append-only log: it touches free text only, never a field progress is derived from (recorded in the decision record). A redacted event still parses (`text` may be empty in the schema; the push refuses empty text).
- **Export** includes the events (with text), the `doubts` rows, the AI calls and the limit override. **Delete** cascades `doubts` and the override; `ai_calls.learner_id` is set to null (cost reports keep tokens); jobs hold only doubt ids.

## Review Focus

1. **A prompt-injection doubt** ("ignore your instructions… `</doubt>` …"): the request the fake provider received has exactly one `</doubt>`, the student text is inside it, and the system prompt is unchanged. Task 9.
2. **A doubt with a phone number, an email and the student's own name**: the fake provider's received `user` text contains `[फ़ोन नंबर]`, `[ईमेल]` and `[नाम]` and none of the originals; the stored doubt keeps the original. Task 9 (`masking end to end`, `masks the learner's own name`).
3. **A distress doubt asked offline that syncs a day later**: the phone shows the helplines before any sync; after the push the answer is the helpline reply, the student is flagged `safeguarding`, and the email says the doubt was asked yesterday (IST) and received today. Tasks 2, 10, 13.
4. **The AI provider down for an hour**: the push succeeds at once, jobs retry with backoff, the answer arrives once after recovery, the student keeps learning. Tasks 3, 9.
5. **The same `doubt_asked` pushed twice** (retry, two phones): one `doubts` row, one AI call, one answer event, one email. Tasks 8, 9, 10.
6. **`ai_doubts` switched off, from an un-synced phone**: the push is accepted, the AI is not called, the answer outcome is `off`. Task 8.
7. **A student deleted while their doubt job is queued**: the answer job and the email job complete without calling the AI or sending, and nothing of theirs is left (all-columns search). Tasks 9, 10.
8. **A mentor outside the cohort reading doubts** by id, by student, by flag or through PostgREST: `FORBIDDEN` (RLS: nothing). Tasks 5, 7, 10, 11.
9. **Doubts and answers in export, delete and retention**, including a doubt 13 months and a day old. Task 5.

1. **Schedule vs. GitHub minutes (conflict with the brief's "every 5 minutes").** The repository is private on the free plan: 2,000 Actions minutes a month, and each run bills at least one minute. Every 5 minutes is about 8,600 minutes a month. This plan runs jobs right after every push in the Edge Function, so answers come in seconds and the schedule is only the retry net; every 30 minutes is about 1,450 minutes plus the nightly backup. A safeguarding alert then goes within seconds of the sync when the push's background run sends it, and at worst within 30 minutes. The background run starts after the push has answered, so the series map's "never sent inline from a request" still holds. 6a uses the same `background` hook after a booking and a cancel, so Meet links also arrive in seconds and the series needs no faster schedule.
2. **Email over the Gmail API, not SMTP (the series map's "Workspace SMTP adapter" is updated to match).** Supabase Edge Functions block outbound SMTP ports 25 and 587, so SMTP could only run from the scheduled workflow, and the alert would wait for it. The Gmail API is HTTPS, runs in both places, and needs no app password (which some Workspace admins disable). The cost is a one-time admin step: a service account with domain-wide delegation limited to `gmail.send`. The `Email` port that 6a consumes is unchanged.
3. **Shared-interface additions (additive; the series map now states them):** `claimDue` takes an optional `kinds` filter (so the Edge Function never claims an email job it cannot send); `JobRepo.deadCount()` and `prune()`; a handler may take a second argument `{ id, attempts, final }`; a new job kind `doubt_answer`. **`dedupeKey` does not ignore dead jobs:** a key is used once, whatever the job's state (done and dead included), so a deliberate re-run needs a fresh key (6a's retry and reconnect use `calendar_event:<bookingId>:<now ms>`).
4. **The append-only log gets one exception:** retention blanks doubt and answer text in events older than 13 months. Progress fields are never touched.
5. **Deleting a student on request also stops their unsent safeguarding alert** (the job finds no doubt). If the NGO wants alerts to outlive a deletion, the email job would need to carry the text, which the payload rule forbids.
6. **Structured outputs are not used:** the shared `AIRequest` has no schema field, so the model is told to reply in JSON and the server validates it. If the eval shows malformed replies, add an optional `jsonSchema` to `AIRequest` (5b may want it too).
7. **Job payload strings are limited to 64 characters without spaces or `@`** (`assertIdsOnly`). Resolved with 6a: its `calendar_cancel` payload's `eventId` is always 6a's own id (the booking uuid without dashes, 32 characters), not a Google-generated one, and must stay in the payload because a deleted learner's booking row is gone by the time the job runs. 5b's payload is a uuid and a date.
8. **Lesson text source:** the spec says "the published bundle"; the bundles are on the app's host (Cloudflare Pages), not Supabase Storage, so the server reads them from `CONTENT_BASE_URL`.
