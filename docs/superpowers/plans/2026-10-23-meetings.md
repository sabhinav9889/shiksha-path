# Mentor Meetings Implementation Plan (Plan 6a)

> **Status, 2026-10-30:** built in a reduced form (slots, booking, cancel, no calendar integration,
> no repeating slots, no outcomes or notes). See
> [the decision](../../decisions/backend-2026-10-30-slot-booking.md). The rest of this plan is
> still the plan for those parts.

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Also follow `AGENTS.md`. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Students book 1-to-1 meetings with their cohort's mentors. Each meeting gets a Google Calendar event with a Meet link on the mentor's own calendar. This plan also covers the booking rules, outcomes and private notes, and lets a backup-code student add Google sign-in.

**Architecture:** Same shape as Plans 4a to 5b:

- **Calendar connection:** a mentor connects Google Calendar through a **separate** OAuth authorization-code flow (staff sign-in keeps `email profile`). The refresh token is stored AES-GCM encrypted under `MEETINGS_TOKEN_KEY`.
- **Booking:** one service applies every booking rule with the `Clock` port. Postgres backs it up with a partial unique index (one live booking per slot) and a per-learner advisory lock (the cap on upcoming bookings).
- **Calendar work:** never done inside a request. The booking enqueues a `calendar_event` job and a cancel enqueues `calendar_cancel` (5a's `server_jobs` runner). The handlers call the `Calendar` port (a fake, plus a `fetch`-only Google adapter).
- **Adding Google** re-points the learner's one identity row from the code user to the Google user. The learner id never changes, and the code is retired.
- **Screens:** the student screen is a lazy chunk with an offline cache. Staff screens join the staff chunk, and the 4b/5a hooks (`DASHBOARD_CARDS`, `STUDENT_SECTIONS`, "सेटिंग") get one entry each.

**Tech Stack:** Unchanged: Svelte 5, Vite PWA, Dexie, Supabase (Postgres, Auth, Edge Functions), `postgres`, Zod 4, Vitest, Playwright. Google Calendar is called with plain `fetch` and AES-GCM uses WebCrypto (Deno and Node both have it). **No new dependencies.**

**Spec:** `docs/superpowers/specs/2026-10-15-learning-platform-design.md`:

- §10.1 (1-to-1 meetings) and §10.3 (data and RLS);
- §11 rows "Slot taken just before booking", "Google Calendar/Meet creation fails" and "Mentor's Google connection expired";

- §5.3 (code students add Google before booking) and §9.1 (the Doubt-meeting button);

Rules: `security.md` ("mentors add Calendar for their own calendar only"; rate-limit bookings), `privacy.md` (a new personal-data flow: the student's email goes to Google Calendar), `database.md`, `testing.md` ("booking rules").

## Global Constraints

Everything marked _(builder's call)_ is open in the spec. ⚑ marks values for the owner to confirm (see the closing section).

- All earlier global constraints still apply: TypeScript strict; Zod at every boundary; parameterised SQL only; RLS on every table with a policy per role; nothing personal in logs or URLs; secrets only in env; Hindi first with English beside it; no stack traces to clients; ports and adapters (no Google import or call outside `adapters/google-calendar.ts`); code limits (file ≤ 300, Svelte ≤ 200, function ≤ 50, params ≤ 4).
- **Series constraints 1–11** (series map) apply verbatim:
  1. contract tests on memory **and** Postgres with more rows than one page;
  2. an old phone never loses new server data;
  3. derived data corrected on read;
  4. revocation tested;
  5. shared phones (idle guard, no secrets in `localStorage`);
  6. six personal-data steps;
  7. one audit entry per staff write route;
  8. traceability;
  9. first-load ≤ 120 KB with a size step;
  10. no names in URLs;
  11. server-side `FEATURE_OFF`.
- **Booking rules** (spec §10.1; `org_settings` keys with these defaults ⚑):
  - `booking_min_hours_ahead` = **24**: a slot may be booked when `startsAt − now ≥ 24 h`;
  - `booking_max_days_ahead` = **14**: a slot may be booked when `startsAt − now ≤ 14 × 24 h`;
  - `booking_cancel_hours_before` = **2**: a student may cancel while `startsAt − now ≥ 2 h`;
  - `booking_max_upcoming` = **2**: the count of the learner's `booked` bookings whose slot has not started.

  Boundaries are inclusive at exactly 24 h, 14 d and 2 h. A mentor may cancel any time before the start _(builder's call)_.

- **Slots:** a date plus an IST start time, length **30 min** by default (allowed 15–120 in steps of 15).
  - **Weekly repeating** _(builder's call)_ creates one row per week for `weeks` ∈ 1–12 (default 8), sharing a `series_id`. Real rows keep the double-booking guarantee on one row, and need no nightly generator.
  - One mentor's slots may not overlap _(builder's call: checked under a per-mentor advisory lock)_.
- **Topics:** `doubt | progress | career | resume` → "डाउट / सवाल · Doubt", "प्रगति पर बात · Progress review", "करियर सलाह · Career advice", "रिज़्यूमे बनाना · Resume building". The student's note is ≤ **280** characters.
- **Mentor cancel reason** is a pick list, not free text _(builder's call: no unmoderated text from staff to minors)_: `mentor_unavailable | emergency | rescheduling | other`. The system reasons are `mentor_left | student_paused`.
- **Outcome:** `done | no_show`, only once the slot has started. The private note (`meeting_notes.body`, 1–1000 characters) is visible to in-scope staff and never to students.
- **Who sees whose slots:** a student sees a slot only when all of these hold:
  - its mentor is `active`;
  - the mentor teaches the student's cohort (`staff_cohorts`);
  - the mentor's connection `status = 'ok'`;
  - the slot is not removed, starts inside the booking window, and has no live booking.
- **Calendar scope** ⚑: `openid email https://www.googleapis.com/auth/calendar.events.owned`.
  - Google lists `calendar.events.owned` as "See, create, change, and delete events on Google calendars you own". It is accepted by `events.insert` and `events.delete`.
  - It is narrower than `calendar.events` ("all your calendars").
  - `openid email` lets the server check that the connected account is the mentor's own staff email. Verified 2026-10-24 at developers.google.com/workspace/calendar/api/auth.
- **OAuth:**
  - authorization at `https://accounts.google.com/o/oauth2/v2/auth` with `response_type=code`, `access_type=offline`, `prompt=consent`, `include_granted_scopes=false` and a signed `state`;
  - tokens from `https://oauth2.googleapis.com/token`; revoke at `https://oauth2.googleapis.com/revoke`;
  - redirect URI = env `GOOGLE_CALENDAR_REDIRECT_URI`, the app origin with a trailing `/`. Google forbids fragments, so the app reads `?code&state`;
  - a refresh answering `invalid_grant` means the connection expired.
- **Events:**
  - `events.insert` on `calendarId=primary` with `conferenceDataVersion=1` and `sendUpdates=all`;
  - our own event `id` = the booking uuid without dashes. It is valid base32hex (0-9a-f ⊂ 0-9a-v), so a retried insert is detected;
  - `conferenceData.createRequest = { requestId: <bookingId>, conferenceSolutionKey: { type: 'hangoutsMeet' } }`;
  - the Meet link is the `conferenceData.entryPoints[]` item with `entryPointType: 'video'`. While `createRequest.status.statusCode` is `pending` it stays null and the job retries;
  - title: `Shiksha Path: <topic in Hindi> — <student name>`. The description holds no note text _(builder's call: the note may hold a doubt; the mentor reads it in the app)_;
  - cancel = `events.delete` with `sendUpdates=all`, where 404 and 410 count as done.
- **Token at rest:** `token_enc = "v1.<keyId>.<base64url iv>.<base64url ciphertext>"`.
  - AES-256-GCM with a 12-byte random IV, and AAD = the `staff_id`.
  - `keyId` = the first 8 hex digits of SHA-256(key).
  - `MEETINGS_TOKEN_KEY` is 32 bytes in base64. The optional `MEETINGS_TOKEN_KEY_OLD` is only for decrypting during rotation.
  - The plain refresh token never appears in the DB, logs, errors, audit, exports or the app bundle.
- **Meet links shown on the phone** must match `^https://meet\.google\.com/[a-z0-9-]+$` (DB check and Zod). Anything else is not shown.
- **Code student → Google** (security-reviewer must review):
  - a one-time **link ticket** of 32 random bytes (base64url) is valid **10 minutes**; only its SHA-256 is stored;
  - the learner id never changes;
  - after success the code is **retired** ⚑: its `login_codes` row and code auth user are deleted, so every code session ends;
  - refused: a Google account already linked to another learner (`GOOGLE_TAKEN`), and a staff Google account or one matching a staff invite (`FORBIDDEN`).
- **New error codes** (`api-contract/errors.ts` and `respond.ts`):

  | Code                     | Status |
  | ------------------------ | ------ |
  | `SLOT_TAKEN`             | 409    |
  | `BOOKING_WINDOW`         | 409    |
  | `BOOKING_LIMIT`          | 409    |
  | `CANCEL_TOO_LATE`        | 409    |
  | `NEEDS_GOOGLE`           | 403    |
  | `GOOGLE_TAKEN`           | 409    |
  | `CALENDAR_NOT_CONNECTED` | 409    |
  | `CALENDAR_WRONG_ACCOUNT` | 403    |

  Each has a plain Hindi + English message in the lazy chunk that shows it (never a code).

- **Rate limit:** `LIMITS.booking = { limit: 20, windowSeconds: 86_400 }` on bucket `booking:<learnerId>`, covering book and cancel.
- **Feature switch `mentor_booking`:** the list and book routes call `requireFeature` first. Cancel stays allowed _(builder's call: a student can always free a mentor's time)_.
- **Retention** ⚑:
  - bookings (and their notes) are deleted **13 months** after the slot time;
  - unbooked slots 30 days after their time;
  - link tickets 1 day after expiry;
  - a connection lives until disconnect or the mentor leaves.

  All of these are applied by `runRetention` (the nightly `admin -- retention`).

- **Audit actions added:**

  | Action                  | `details`                  |
  | ----------------------- | -------------------------- |
  | `calendar_connected`    | `{}`                       |
  | `calendar_disconnected` | `{}`                       |
  | `slots_published`       | `{ count, seriesId }`      |

  `FORBIDDEN_KEYS` gains `note`, `body` and `email`.

- **Phone:** route `#/meetings` loads `screens/meetings/MeetingsScreen.svelte` lazily. The home card is the only first-load addition (< 1 KB). The last list is cached in the profile's `meta` store (`meetings:<learnerId>`); booking and cancel need internet ("इंटरनेट चाहिए").

## Review Focus

1. **Two students racing for one slot** (Postgres): exactly one `booked` row; the other gets `SLOT_TAKEN` and the phone shows "यह समय अभी किसी और ने बुक कर लिया" and reloads. Task 4 (`two bookings of one slot at once…`), Task 13.
2. **Booking and cancel windows:**
   - booking at 24 h − 1 min is `BOOKING_WINDOW`, and at exactly 24 h it books;
   - cancelling at 2 h − 1 min is `CANCEL_TOO_LATE`, and at exactly 2 h it cancels;
   - a third upcoming booking is `BOOKING_LIMIT`, including two parallel bookings by one student on Postgres.

   Task 1 (table), Task 7.

3. **A mentor who leaves** (deactivated, or removed from the cohort): their slots vanish for students at once; future bookings are cancelled as `mentor_left`, with a `calendar_cancel` each; students see "मेंटर अब उपलब्ध नहीं हैं"; the connection is revoked and deleted. Task 10.
4. **An expired Google connection mid-booking:**
   - the `calendar_event` job meets `invalid_grant`;
   - the connection turns `expired` and the mentor's slots are hidden;
   - the booking stays `booked` with no link and `calendar_problem = 'expired'`;
   - the mentor sees "Google Calendar फिर से जोड़ें", and reconnecting re-queues the link.

   Task 8.

5. **Calendar API down for a day:** the booking stays "मीट लिंक जल्द आएगा", is retried with backoff and marked `unavailable` for the mentor. After the jobs die, the mentor's "फिर कोशिश करें" creates it, with no duplicate event (same event id). Task 8.
6. **A student deleted with a future booking:**
   - the event is cancelled through a `calendar_cancel` job whose payload holds only `{ mentorId, eventId }`;
   - a `calendar_event` job finishing after the deletion cancels the event it just made;
   - no row holds the id (the all-columns search).

   Tasks 8, 10.

7. **A code student trying to book:**
   - the phone shows "बुक करने के लिए पहले Google जोड़ें";
   - the server answers `NEEDS_GOOGLE` even to a hand-made request;
   - after adding Google, the same learner id books, the old code answers `BAD_CODE`, and an un-synced phone on the old code keeps its pending events until restored with Google.

   Tasks 7, 11, 12.

8. **A Google account already linked elsewhere trying to link:** `GOOGLE_TAKEN`; nothing changes for either learner; the profile gets its code session back. The same goes for a staff Google account and a reused or expired ticket. Tasks 11, 12.
9. **A refresh token never appearing** in logs, errors, audit, exports, `server_jobs` payloads or `last_error`. A test plants a marker token and searches every sink. Tasks 2, 5, 8, 10.
10. **The switch and stale caches:**
    - `mentor_booking` off for one student refuses list and book from an un-synced phone (`FEATURE_OFF`);
    - a cached list 3 days old shows a meeting whose time has passed as past, without "Join Google Meet".

    Tasks 7, 13.

## Notes for the owner

- **"Mentor can reissue" a code after a Google link conflicts with the data model.** A learner has exactly one identity (`learner_identities.learner_id unique`), and Plan 3b's `issueCode` refuses a learner who has one. Reissuing a code would mean un-linking Google. This plan retires the code and does not build reissue. A student who loses their Google account is helped by an admin through deletion-and-re-enrol, or by a later "replace sign-in" plan.
- **Spec §5.4 says an Edge Function creates the event "on booking".** This plan does it in a `calendar_event` job (series map: jobs, never inline), which the Edge Function runs in the background right after the booking answers (5a's `background` hook), so the link normally arrives within seconds. If that run fails or is cut off, the 30-minute `run-jobs` schedule retries it. Until then the student sees "मीट लिंक जल्द आएगा", which is the spec's own §11 wording.
- **Spec §12's integration test "against a test Google Workspace account"** cannot run in CI (no live calls). It becomes the runbook's `calendar-smoke` check, run by the owner after setup and after any adapter change.
- **5a's backoff gives up in well under a day** (8 attempts, about 8.5 h), so the "Calendar down for a day" case relies on the mentor's retry button and on reconnect re-queuing. If the owner prefers automatic recovery, 5a's runner would need a longer cap for `calendar_*` kinds.
- **The brief asked for "DASHBOARD_CARDS entries".** This plan adds one card showing booked, done and no-show together (spec §8.1 lists them as one item). Splitting it into three is a one-line change if wanted.
